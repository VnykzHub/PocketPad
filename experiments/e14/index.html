E14 - Mixed content and private-network reachability

This probe checks the assumption behind the dev/production split: an HTTPS page must not be able to reach an http:// or ws:// service on the LAN. The expected result is that the first two attempts below are blocked and the localhost control is allowed, because loopback is treated as a trustworthy origin.

Nothing runs on page load. Each attempt starts only when you press its button. The page sends no application data, uploads nothing, sets no cookies and stores nothing; results stay on this page until you copy them. An attempt times out after 4 seconds.

2. What you need

  1. Start the dev server on the LAN from the repository root: node packages/dev-server/dist/main.js. The default port is 8080 and the terminal prints the LAN URL.
  2. Start an HTTPS tunnel to that same port. This probe never installs or starts a tunnel; run one manually: 
    cloudflared tunnel --url http://localhost:8080
# or
ngrok http 8080
  3. Open this page through the tunnel: https://<tunnel-host>/x/e14/. The page must be loaded over HTTPS for the mixed-content result to mean anything.
  4. Enter the dev server's LAN WebSocket URL, for example ws://192.168.1.10:8080/ws, and press one of the test buttons.

If you have no tunnel, you can still use this page to validate the URL format, inspect the current page context, and run the localhost control from a browser on the dev-server machine.

How to read the result

  • ws:// LAN WebSocket - expected to be blocked on an HTTPS page. A synchronous SecurityError from the constructor is Chromium's mixed-content rejection. Other browsers may fire an error event instead; the console holds the reason.
  • http:// LAN /healthz - expected to be blocked as mixed content. The dev server's CSP also lists only 'self' and ws: under connect-src, so this attempt can be blocked by CSP first; the page reports that separately when it sees a securitypolicyviolation event.
  • ws:// localhost control - expected to connect when the dev server runs on the same machine as the browser and this page is open at an origin the server allows (the printed LAN URL or http://localhost:8080). The reliable control run is http://localhost:8080/x/e14/ on the dev-server machine. Through the HTTPS tunnel the browser sends the tunnel origin, which the dev server rejects at the WebSocket upgrade (SR-11), so a close before open with code 1006 there is an origin check, not mixed content. The server also rejects 127.0.0.1 for the same reason. On a phone, localhost is the phone itself, so a failure here is not evidence about the LAN result.
  • Elapsed time - measured with performance.now() around the attempt. A timeout is not proof of a block; an unreachable host also times out.
